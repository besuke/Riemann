# 並列・分散計算基盤と計算コアの設計方針

この文書は全体構想と開発方針を記録する。実装は段階的に進め、今すぐ GPU 対応や既存コードの全面改修には着手しない。当面はコンテンツの実装を優先する。

記述の区分は `docs/specification.md` 1.4 節に従う。【ソース確認】は現在のコードで確かめた事実、【設計案】は将来の方針で未実装である。性能についての主張は、実測するまで仮説として扱う。

## 1. 位置づけ

RiemannFinMath は、LagrangeFinance の冒頭と Part III で述べる並列・分散金融計算基盤の**計算コア**である。

【設計案】将来は Azure 上の Linux マシン群で、次のように動かす。

1. **R（管理側）**：データ、シナリオ、タスクを tibble で作り、検証し、分類して管理する。
2. **配布**：`furrr::future_map()` と `future.batchtools` で、タスクを Slurm のジョブとして投入する。
3. **実行（ワーカー）**：各ワーカーの R プロセスが RiemannFinMath を呼び、Rust コアが計算する。
4. **回収**：結果を R に戻し、タスクの識別子で突き合わせる。

## 2. Linux を本番環境とする利点【設計案】

複数マシン・多数コアの資源管理と、実行基盤の観点からの利点である。

| 観点 | 利点 |
|---|---|
| ジョブ管理 | Slurm は Linux を前提とする。ジョブ配列、依存関係、再投入、優先度、会計記録（`sacct`）をそのまま使える。`future.batchtools` は Slurm の雛形でジョブを投入できる |
| 資源の上限 | Slurm は cgroup でジョブごとの CPU 数とメモリーを強制する。割り当てを超えたスレッドやメモリーは、そのジョブの中に閉じ込められ、他のジョブに影響しない |
| CPU の配置 | `--cpu-bind` や NUMA の指定で、スレッドを物理コアとメモリーの近くに固定できる。多コア機で、メモリー帯域の取り合いを減らせる |
| 環境の均一性 | 同じ OS イメージやコンテナ（Apptainer など）をすべてのノードに配れる。R、Rust ツールチェーン、ライブラリの版を固定し、結果の再現性を保てる |
| プロセスの扱い | fork による R のプロセス並列（`future` の `multicore`）が使える。Windows では使えない |
| 共有ストレージ | NFS や Azure の共有ファイルシステムに、batchtools のレジストリー（タスクと結果の置き場）を置ける |
| 計算資源の種類 | Azure の HPC 向け VM や GPU ノードを Slurm の分割（partition）と `--gres` で使い分けられる。中断されうる安価なノードも、再投入を前提に使える |
| 実行の妨げ | 開発機（Windows）では、新しくビルドした実行ファイルがアプリ制御でブロックされた（2026-11-03、`CLAUDE.md` に記録）。サーバー用の Linux イメージでは、署名の扱いを含めて実行の可否を自分で管理できる |

## 3. 並列の階層と資源の割り当て【設計案】

並列は 3 つの層に分け、**同じ CPU を二つの層で取り合わない**ことを原則とする。

| 層 | 担い手 | 単位 | 割り当て |
|---|---|---|---|
| ノード間 | Slurm（`future.batchtools`） | ジョブ（またはジョブ配列の要素） | `--nodes`、`--ntasks`、`--cpus-per-task`、`--mem` |
| ノード内のプロセス | R の `future`（`multicore` または `multisession`） | R プロセス | 割り当てられた CPU の中で |
| プロセス内のスレッド | Rust の Rayon | スレッド | 割り当てられた CPU の中で |

**R のプロセス並列と Rust のスレッド並列を区別する。** 1 つの Slurm タスクに `c` 個の CPU が割り当てられたとき、次のどちらかにする。

- **A. 1 プロセス × `c` スレッド**：R プロセスは 1 つで、Rust に `threads = c` を渡す。大きな配列をまとめて計算する場合（多数のパス、多数の銘柄）に向く。メモリーは 1 プロセス分で済む。
- **B. `c` プロセス × 1 スレッド**：R プロセスを `c` 個にし、Rust は `threads = 1` とする。R 側の前後処理が重い場合や、タスクが小さく多数ある場合に向く。

**両方を同時に `c` にしてはいけない**（`c × c` スレッドになり、過剰に割り当てる）。A と B は当面の運用規則で、分かりやすさのために両端だけを選ぶ。一般には「R のプロセス数 × 各プロセスの Rust のスレッド数 ≤ 割り当てられた CPU 数」を満たせばよく、将来は中間の組み合わせ（例：`c = 16` に 4 プロセス × 4 スレッド）も選べる。どれがよいかは、メモリー量とタスクの大きさから決め、実測で確かめる。R が使う BLAS（OpenBLAS など）のスレッドも `OMP_NUM_THREADS=1` などで止め、Rust のスレッドとの重なりを避ける。

**CPU 数の取得**：R 側では `parallelly::availableCores()` を使う。Slurm の `SLURM_CPUS_PER_TASK` や cgroup の上限を考慮するためである。その値を Rust の `threads` に明示的に渡す。

**現状**【ソース確認】：`crates/riemann/src/batch.rs` の `map_parallel` は、`threads = 0` のとき Rayon の既定値を使う。Rayon の既定値が cgroup や Slurm の割り当てを反映するかは確かめていない【未確認】。そのため本番では `threads = 0` に頼らず、R から明示的に渡す方針とする。

**メモリー**：Rust の計算で確保する量は、ほぼ入力の大きさで決まる（例：Longstaff–Schwartz はパス数 ×（ステップ数 + 1）の f64 で、上限 20 億値を入力境界で検査している【ソース確認】）。R 側でタスクの大きさを分割し、1 タスクが `--mem` の中に収まるようにする。分割の大きさは、要素あたりのメモリー量の見積もりから決める。

**再現性**：疑似乱数は、パスと次元の番号から計算する方式で、スレッド数や実行順に依存しない【ソース確認】（`crates/riemann/src/math/random.rs`）。この性質を使い、パスの番号の範囲をタスクに分けて配れば、1 台で計算した場合と同じパスになる【設計案】。Sobol 列も、先頭からの点の位置でタスクに分けられる（Longstaff–Schwartz の `Separate` は既に開始位置を指定している）。

**失敗と再投入**：タスクは同じ入力から同じ結果を返すように作り、結果はタスクの識別子で回収する。途中で中断されたノードのタスクは、そのまま再投入できる。

## 4. 開発方針：入口は厳格に、計算コアは単純に

目的は、コンパイル後の実行性能を高めることである。

### 4.1 R 側：明示的なスキーマと一括検証

1. **スキーマ**：tibble の列ごとに、名前、型、単位、欠損の可否、制約（正の値、範囲、日付の順序など）を明示する。
2. **一括検証**：入力の境界で、型・欠損・制約をまとめて検証する。誤りはここで行ごとに報告し、計算コアに渡さない。
3. **分類**：商品・モデル・計算方式ごとに分類する（例：`group_by()` と `nest()`）。
4. **連続配列で渡す**：Rust には、分類した単位ごとに、同じ型の連続配列（列ごとの `Vec<f64>` など）として渡し、まとめて計算する。

### 4.2 Rust 側：分岐と変換を計算の外に出す

- 計算の内側で、要素ごとに型・欠損・妥当性・商品種別を繰り返し判定する構造は避ける。これらは入力境界で一度だけ行う。
- 不要な分岐、変換、メモリー確保を減らす。ループの中で文字列の解析（例：`"call"` / `"put"`）や列挙型への変換をしない。
- データは列ごとの連続配列（構造体の配列ではなく、配列の構造体）に置き、CPU の SIMD による自動ベクトル化と、Rayon による分割を適用しやすいループにする。

**この方針の範囲**：

- 型推論そのものには実行時の負担はない。型を書き分けることが目的ではない。
- `if` を一律に禁止するものではない。モデルや数値解法に必要な判定（行使の判定、解の探索の収束、小さな値の級数展開など）は残す。入力の曖昧さを補うためのチェックを、計算コアに散在させないという方針である。
- tibble 自体が SIMD を保証するわけではない。性能は Rust 側の配列配置と、実測結果で判断する。

**実測**：ベンチマーク（`criterion` など）で前後を比べ、ベクトル化されたかはアセンブリーや性能計測で確かめる。本番の VM の CPU が揃っていれば、命令セットを指定したビルド（例：`-C target-cpu=x86-64-v3`）も検討する。`exp`、`ln`、正規分布関数などの数学関数は、通常スカラーで呼ばれ、自動ベクトル化の妨げになりやすい。効果は実測で確かめる。

### 4.3 現状との差【ソース確認】

既存のコードには、この方針と違う箇所がある。全面改修はせず、性能が問題になった箇所から直す。

| 箇所 | 現状 | 方針との差 |
|---|---|---|
| 債券・カーブのバッチ（`batch.rs`） | 銘柄ごとの構造体（`BondEvaluation`）の配列を Rayon で分割 | 構造体の配列。銘柄ごとに債券を組み立てる |
| R の関数の多く（例：`compute_hull_white_bond_option_value`） | 行ごとに `names::parse_option_type` で文字列を解析 | 文字列の解析が計算のループの中にある |
| モンテカルロ（`options.rs`、`prdc.rs`） | パスを連続したベクトルとして持つ | 方針に近い |
| Longstaff–Schwartz | パスを行優先の連続配列に置き、設定は計算の前に一度だけ検査する | 方針に近い。回帰は日付ごとに逐次 |

## 5. GPU（CUDA）実行の構想【設計案】

### 5.1 CPU 並列との区別

- **現在**：Rayon による CPU のスレッド並列。データは主記憶にあり、スレッドが分担する。
- **GPU**：同じ処理をする大量のデータをまとめて GPU に転送し、商品・計算方式ごとの専用カーネルで一度に計算し、結果を戻す。CPU 側で検証・分類した型付き配列を、まとめて転送する。

目的は、スレッド間で処理が分かれる（分岐で別々の経路をたどる）ことと、CPU と GPU の間の細かな転送を減らすことである。GPU では、同じカーネルの中で要素ごとに処理が分かれると、まとめて実行できず遅くなる。そのため 4 章の「同じ処理をするデータをまとめる」設計は、GPU ではより重要になる。

### 5.2 GPU 化の候補

| 計算 | 候補か | 理由 |
|---|---|---|
| モンテカルロのパス生成と payoff（European、PRDC） | 有力 | パスが互いに独立で、同じ処理を大量に繰り返す。乱数がパスと次元の番号から決まるので、GPU でも同じ値を作れる |
| Sobol 列とパス生成 | 有力 | 点の位置から直接計算できる（Gray code による逐次更新の代わりに、点の番号から直接求める形が必要） |
| Longstaff–Schwartz | 部分的 | パス生成と payoff、継続価値の評価は GPU 向き。各日の回帰は小さな正規方程式で、パスにわたる和（縮約）を GPU で、解くのを CPU で行う分担になる |
| Hull–White の状態格子 | 部分的 | 各ステップの状態ごとの期待値は並列にできる。ステップの間は逐次 |
| 多数の閉形式（Black、債券価格） | 要検討 | 計算が軽く、転送の費用に見合わない可能性がある。大量にまとめた場合に実測で判断する |
| カーブの構築、校正、日付・カレンダー | 対象外 | 逐次の解法や分岐が多く、GPU に向かない |

### 5.3 追加実装が必要な箇所

- **列ごとの配列を受け取る計算の入口**：既存の関数とは別に、分類済みの連続配列を受け取る層を作る（CPU 版と GPU 版で同じ形にする）。
- **GPU 用のクレート**：このライブラリは `#![forbid(unsafe_code)]` である。CUDA の呼び出しには `unsafe` が要るので、GPU は別のクレートに分け、そのクレートの FFI 境界でだけ `unsafe` を認める。Rust から CUDA を使う方法（`cudarc` など）、または C++ の CUDA を FFI で呼ぶ方法は、着手時に選ぶ。
- **機能の切り替え**：Cargo の feature で GPU 版を選べるようにし、GPU がない環境では CPU 版に戻る。
- **乱数**：番号から直接求める Sobol 列の実装（現在は逐次更新）。
- **縮約の順序**：浮動小数点の和は順序で結果が変わる。再現性のため、縮約の順序を固定する方法を決める。
- **倍精度の性能**：金融計算は f64 を前提とする。GPU の f64 性能は機種で大きく違う（データセンター向けの機種は高く、一般向けの機種は低い）。Azure の GPU VM の機種は、f64 の性能で選ぶ。
- **検証**：GPU 版は、CPU 版と同じ golden テストで、許容差を決めて照合する。

## 6. 当面の扱い

- GPU 対応、既存コードの全面改修には、今は着手しない。
- 新しく実装する計算（MBS、LMM など）は、可能な範囲で 4 章の方針（入口で検証、計算は連続配列）に沿って書く。
- 本番化の前に行う小さな作業の候補：`threads = 0` の扱い（Slurm の割り当てを確かめるか、R から常に明示する）、パスの番号の範囲によるタスク分割の関数、Slurm 用の `future.batchtools` の雛形と実行例。
